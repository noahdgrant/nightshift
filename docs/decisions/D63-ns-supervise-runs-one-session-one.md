# D63: ns-supervise runs one session one level above ns watch for a night

## Decision

`ns-supervise` (#345) runs one session one level above `ns watch` for a night. It asks whether the operator is around (no answer: away), attaches to a running night or starts one (the installed `ns-watch.service`, else `systemd-run --user` with the OOM-safe settings of `contrib/systemd`, else it asks the operator), follows `ns log -f --json`, and runs a slow check about every 20 minutes for the unit's state, silence and forge labels. It pings on a stuck or budget unit, a PR that needs a human merge, a `ready-for-human` issue, a night that dies early, a usage-limit pause or the harness breaker, and `[supervise] silence_minutes` (45) of silence while units run (the newest `ts` in its own `ns log -f` stream; `ns status --json` only confirms units are running). Pings go to the harness's notification, the supervisor's thread and an optional `[supervise] notify` command. Each ping has a key (trigger kind plus unit or issue) recorded in its Timeline line, and a key already there is not pinged again, so the slow check and a re-attach never repeat a ping. It starts its transient unit without `--collect`, so a failed night keeps its `Result`; a failed `ns-watch-supervised` is recorded and reset when the next night starts. It is read-only except for starting and stopping a night. It stops one only when the operator is away and the failure is factory-wide (red `main` after a factory merge, found by the runs for the merge sha, three units in a row stuck for the same reason, a failed self-update or more than two self-updates in an hour, repeated OOM kills); when the operator is around these are pings, and a single stuck unit is always a ping. It keeps an uncommitted report at `<git-common-dir>/ns/handoffs/<night>.md`, continued by a supervisor that re-attaches; events the report's Timeline already records are not handled again, and the stuck streak counts only the newest consecutive `end` events.

## Reason

Agreed in #335. Watching and doing the operator's work (merges, hand fixes, design sessions) in one session mixed two jobs, so the supervisor only watches and the operator works from its report in another session. A stop needs a failure that would waste the rest of the night on every unit, and an absent operator; one stuck unit costs one unit, and `ns watch` already moves on. `systemctl --user stop` requeues unfinished units (#209), so a stop loses no work. The report sits under the git dir like the run log, because it describes one machine's night, not the repo. `[supervise]` lives in `nightshift.toml` so a repo's notify command travels with its factory; the skill reads it through `ns factory validate`, and `ns run` and `ns watch` ignore it. The skill is model-invoked, unlike `ns-auto`: it starts at most a night the operator asked for and does no work of its own. `nightshift.toml` has no `--until` key, so a night the prompt gives no end runs to 06:30, the packaged service's end. Its evals run against fake `systemctl`, `systemd-run`, `journalctl`, `gh` and `ns` (`evals/fakes/systemd/`), so no trial can stop a real night or start model runs. The `night-log` fixture puts them first on `PATH` with a new fixture key, `path_prepend`, rather than a capability: an unconfigured capability skips the case, and CI fails on any skip but zephyr's. Spec: `skills/ns-supervise/SKILL.md`, docs/FACTORY.md ("Supervising a night").
