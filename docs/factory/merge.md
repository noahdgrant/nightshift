# Merge

`merge.policy = "human"` (the default) ends a unit at `done` when `pr.md` passes. With `policy = "auto"`, `ns run` then runs its merge step. It is the only code in nightshift that merges, it only merges its own unit's PR, and only with squash.

The steps name the `gh` command each forge call runs on GitHub. The step makes those calls through the `Forge` trait (`cli/src/watch/forge.rs`), like every other forge call in `ns`, and `gh` runs only in the GitHub implementation. GitLab has no merge step yet (#323): its first call fails with "ns run's merge step is not supported on GitLab yet (#323)", and the run exits 1. The steps:


1. `gh pr view <pr> --json state,headRefOid`. `MERGED` already means something other than this step merged it: stuck. Not `OPEN`: stuck.
2. The PR head and `review.md` must be current (see the [state table](run.md)), and `review.md` must be `pass`. Otherwise `done`, needing a human merge. The merge in step 8 matches the PR head, including the head from before a `BEHIND` update when `update-branch` reports none; this goes beyond the issue's literal text on purpose, so a rebase after review still merges the reviewed head.
3. Steps 3 and 4 run without the merge lock, so other units merge while this one updates and waits for CI. The step fetches `origin/<default>` and keeps its tip as the base this round is checked against in step 5 (none when the fetch fails). Then `gh pr view <pr> --json mergeStateStatus`. Right after its base moves GitHub reports `UNKNOWN` while it works the state out, so an `UNKNOWN` is read again with the backoff of step 4, for up to `ci_register_timeout` minutes, after which the step goes on as for any state other than `BEHIND` or `DIRTY`. `BEHIND`: the step first checks whether the commits the PR lacks change any of its files (see ["Updating only on overlap"](#updating-only-on-overlap)). If they don't, it skips the update and goes on with the PR head as it is. Otherwise `gh pr update-branch <pr>`. A failed update, or a head that hasn't moved within `ci_register_timeout` minutes, logs an `update_branch_failed` event with GitHub's error text (and `merge_state` for the head that didn't move). When the base changed a file under `.github/workflows/`, the API updates the branch only if the forge token has the `workflow` scope (a GitHub App needs the `workflows` permission). GitHub refusing for that reason sets `workflow_scope: true` on the event, and the step falls back to git: fetch `origin/<default>`, merge it into the unit branch in the worktree (a merge, never a rebase, so `review.md` and `evidence.md` stay current for an unchanged diff), and `git push --force-with-lease` against the PR head, then goes on as after any update. A conflict in that merge is aborted and goes back to build as `DIRTY` does. Any other failure in the fallback, such as a push the lease refuses, leaves the worktree at the PR head and ends `done`, needing a human merge, with a reason naming the `workflow` scope. `DIRTY`, or any other failed update: back to build with "rebase onto <default> and resolve conflicts" as `{feedback}`, which uses no build attempt when `origin/<default>` moved since the last free rebase (see ["ns run"](run.md), attempts) and a build attempt otherwise. Then, when a gate is set, the PR head must pass it. With `local_queue` on (the default) and a gate set, the step skips update-branch for `BEHIND` and gates the merge result instead (see "Local merge queue"); `DIRTY` still goes back to build, and the steps below are unchanged. Under `[gate] local = "build-only"` the step runs the GitHub merge queue instead, whatever `local_queue` says (see "GitHub merge queue"). The rest of this step is the path with `local_queue = false`, or with no gate. The worktree fast-forwards to the head `update-branch` made, fetching the unit branch from `origin`; a head that can't be checked out ends `done`, needing a human merge. The gate runs there unless it already went green at that head in this invocation. Red goes back to build with its output as `{feedback}`, which uses a build attempt, like a red gate after a phase.
4. GitHub may not have registered checks on a head it just received, so the step first polls `gh api repos/{owner}/{repo}/commits/<sha>/check-runs` and `.../status` for the PR head (the one `update-branch` returned, if it ran) until either reports a check. Polls back off from 5 s to 30 s, bounded by `ci_register_timeout` minutes. None by then: `done`, needing a human merge, with reason "no CI checks registered within <n> min on PR #<pr>; needs a human merge". If the last poll's `gh api` call failed (auth, rate limit, 404) or printed something other than a count, the reason is instead "could not query CI checks on PR #<pr>: <error>; needs a human merge". Then `gh pr checks <pr> --watch`, killed after `ci_timeout_minutes` (stuck). Then `gh pr checks <pr> --json name,state,bucket,link`. No checks at all: `done`, needing a human merge. Any check not `pass` or `skipping`: back to build with the failing check names and the tail of `gh run view <id> --log-failed` as `{feedback}`, then verify, review and ship onto the same PR.
5. Outside the local merge queue, wait while the default branch's CI is red (see ["Red main holds merges"](#red-main-holds-merges)). Then take the merge lock, an OS `flock` on `ns-merge.lock` in the common git dir, held from here until the step ends, so units merge one at a time per repo. While another unit holds it, the step prints `ns run: <unit> merge waits for the merge lock (held by pid <pid>, unit <unit>)`, logs a `lock_wait` event with `phase` and `lock` both `merge`, and tries again every 50 ms, in real time whatever `NS_NOW` says. A stop ends the wait like any other (see ["Units a night didn't finish"](watch.md#units-a-night-didnt-finish)). The wait has no timeout: a live holder only checks and merges, and the kernel drops a dead one's hold. `ns watch --until` bounds it: the run ends as `budget` with `gave up waiting for the merge lock (held by pid <pid>, unit <unit>) at --until` and a `lock_wait_timeout` event with `bound: until`. Under the lock the step fetches `origin/<default>` again. A tip other than the base step 3 kept means another merge landed since this round began. Outside the local merge queue, the step runs the overlap check again against the new tip, and when the new commits change none of the PR's files it merges under the lock without going round. Otherwise it logs `merge_base_moved` (`pr`, `from`, `to`, `attempt`), releases the lock and goes back to step 3, which updates the PR and waits for CI again. A base step 3 couldn't read counts as moved once the tip can be read; a tip that can't be read now counts as no move, and step 7's fetch then ends the unit `done`. After the fifth move the step stops being optimistic. It takes the merge lock before step 3 and holds it through the update, the CI wait and the merge, logging `merge_lock_held_through_ci` (`pr`, `moves`), so no other unit's merge can move the base again. Only a merge from outside `ns` can move it then, and the eleventh move ends the unit `stuck` with "the default branch moved 10 times during this PR's CI, the last 5 with the merge lock held (cap 10)". Then `gh pr view <pr> --json headRefOid`: a head other than the one CI passed on ends `done`, needing a human merge, with "PR #<pr> head moved from <old> to <new> after CI passed on it; needs a human merge". A view that fails, or names no head, leaves that check to `--match-head-commit` in step 8.
6. `gh pr diff <pr> --name-only`. Any path matching a `human_review` glob (`**` crosses directories): `done` with reason "changes files that need human review; needs a human merge (<paths>)". Files that need human review cover the factory's own guardrails: CI config, the definition, the guard and merge code. The rules baseline, `.nightshift/rules-baseline.json`, is the one exception: when it is a hit, the step fetches `origin/<default>` (and the PR's branch, when the worktree lacks the PR head) and compares the baseline at the PR head with the one at its merge base with that tip. When every entry at the head is matched by its own equal entry at the base (all of `tool`, `rule`, `file`, `message` and `snippet`, duplicates counted, so a reordered file counts too), the PR only removes entries: the file is dropped from the hits and the run log gets a `baseline_shrinks` event (`pr`, `path`). An added or changed entry, no baseline at the base, a baseline deleted at the head, one that is not a rules baseline at either end, or a fetch that fails keeps it a hit; when the comparison could not be made, the reason says why ("<path>: cannot tell whether it only removes entries: <error>"). Every other hit still stops the merge, so a shrinking baseline beside another human-review file needs a human as before. `ratchets.json` gets no such exception: loosening a ratchet is a human decision.
7. Marked regions (below): HEAD is diffed against its merge base with `origin/<default>`. A changed line inside a region, in the base or the head version, or an added, removed or moved marker line: `done` with reason "changes code in a human-review region; needs a human merge (<file>:<start>-<end>: <reason>)". If the merge base can't be found, the reason says so and the unit still needs a human merge.
8. `gh pr merge <pr> --squash --match-head-commit <sha>`. If `gh pr view` then reports `MERGED`, the outcome is `merged`, the merge step deletes the remote branch with `gh api repos/{owner}/{repo}/git/refs/heads/ns/<unit> -X DELETE`, and the unit is cleaned up once its quality records are saved (see ["Cleanup"](unit-lifecycle.md#cleanup)). It never passes `--delete-branch`: gh would first check out the default branch in the unit's worktree. A delete that fails, say because the repo deletes merged branches itself, logs `branch_not_deleted` with the error, and the merge stands.

## Local merge queue

GitHub's merge queue tests the merge of a PR with the current default branch, but it needs an organisation-owned repo. Without it, and without "Require branches to be up to date before merging", a PR can merge without ever being tested against the `main` it lands on. Requiring branches to be up to date fixes that, but each merge moves `main` and every other open unit has to update and run CI again. So `ns run` tests the merge result itself before it merges, and the check under the merge lock (step 5) sends the PR round again if the default branch moved since. `[merge] local_queue` turns it on, and is `true` unless set. It needs a gate (see ["Gate"](run.md#gate)): with no gate command, the merge step behaves as with `local_queue = false`.

With the queue on, step 3 goes on after the merge state, without the merge lock:

1. A `BEHIND` PR is not updated. `DIRTY` still goes back to build to rebase.
2. `origin/<default>` is fetched. A failed fetch ends `done`, needing a human merge, with reason "cannot fetch <default> for the local merge queue: ...".
3. When the fetched tip is already in the PR head, the merge would leave the PR head as it is, so the worktree is checked out at the PR head and the gate runs there as with the queue off, skipped when it already went green at that head. A red there logs `merge_gate_failed` too (`reused: false`, since only a green is skipped) and goes back to build with the gate's plain feedback, without the note about combining with `<default>`: the merge result is the PR head.
4. Otherwise a scratch worktree is added at the PR head, detached, at `<git-common-dir>/ns/merge-queue/<unit>`, and the tip is merged into it with `--no-ff --no-commit`. Nothing is committed or pushed. The checkout runs no hook, and a merge that doesn't commit runs none either. The scratch worktree is removed when the step leaves it, whether the gate passed, failed, or a stop ended it; one a killed run left behind is removed before the next is added. A worktree that can't be added, or a merge that fails other than by a conflict, ends `done`, needing a human merge.
5. A conflict goes back to build with "PR #<n> conflicts with <default>: rebase onto <default> ...", the same `conflict` event and `{feedback}` as `DIRTY`.
6. The gate runs in the scratch worktree. Its `gate` event has `phase: merge`, `sha` (the PR head), `base` (the tip of `origin/<default>` it merged), `merge_result: true` and `wall_s`, with the other fields of any `gate` event. Its log is `gate-merge-<n>.log`, numbered by the merge step like the gate on the PR head.
7. Green goes on to step 4 and merges the PR head, which need not be up to date with the base.
8. Red merges nothing. The run logs a `merge_gate_failed` event with `pr`, `sha`, `base` and `reused`, and goes back to build, using a build attempt, with the gate's `{feedback}` plus a note that it ran on the merge with `<default>`, not on the branch alone. The build's reason is "the CI gate failed on the merge with <default>", or names the signal or the memory cap that ended it.

The verdict is kept for the pair (PR head, tip of `origin/<default>`) for the rest of the invocation, except a red that a timeout, the memory cap or a signal caused: it says nothing about the code, so it is not kept and the next merge step runs the gate again. A later merge step that meets the same pair, such as after CI failed on the PR and a rebuild left HEAD alone, reuses it without running the gate, and a reused red logs `merge_gate_failed` with `reused: true`. A new PR head or a moved tip runs it again.

The gate runs without the merge lock, so other units merge while it runs. One that does moves the default branch, and step 5 then sends this PR round again: the gate runs once more on its merge with the new tip. That is the price of testing what lands. The scratch worktree also starts with no build output, so a gate with a build cache in the worktree, such as `cargo`'s `target/`, builds from cold.

Set `local_queue = false` when something else already tests merge results: GitHub's merge queue, a bot that rebases and tests each PR before merge, or branch protection that requires PRs to be up to date with CI on the updated head. Turn it off, too, when the gate is too slow to run again each time another merge lands first. With it off, the merge step updates a `BEHIND` PR and gates the PR head, as described in step 3.

## GitHub merge queue

Under `[gate] local = "build-only"` the merge result is tested on GitHub, not on the laptop. Step 3 goes on after the merge state, without the merge lock; step 5 still makes the merges one at a time:

1. `DIRTY` goes back to ship, not build, with the same `conflict` event and `{feedback}` ("PR #<n> conflicts with <default>: rebase onto <default> and resolve conflicts ..."). Like a conflict that goes back to build, it uses no ship attempt when `origin/<default>` moved since the last free rebase (see ["ns run"](run.md), attempts), and a ship attempt otherwise. Ship merges the base in and resolves the conflict, and a resolution that changes the unit's lines sends it back through verify and review.
2. `BEHIND` is updated as in step 3. Any other state fetches `origin/<default>` and updates the PR the same way when its head doesn't hold the fetched tip, so the merge is tested against the current base even without branch protection that requires PRs to be up to date. In both cases the update runs only when the commits the PR lacks change one of its files (see ["Updating only on overlap"](#updating-only-on-overlap)). A failed fetch ends `done`, needing a human merge, with reason "cannot fetch <default> to update PR #<n>: ...". `update-branch` goes through the API; when GitHub refuses it for the `workflow` scope, the step merges with git and pushes, as in step 3. A failed update or a conflict in the git merge goes back to ship as `DIRTY` does.
3. No local gate runs in the merge step, nor after a ship that moved HEAD: GitHub's checks are the only gate after ship. The gate after build ran the full command, and the gates after verify and review ran the fast one (see ["Where the gate runs all of CI"](run.md#where-the-gate-runs-all-of-ci)).
4. Steps 4 to 8 run unchanged on the updated head, or on the PR head when the update was skipped: the step waits for the PR's checks, bounded by `ci_register_timeout` and `ci_timeout_minutes`, and merges only when every check passed or was skipped. A red check goes back to build with the failing checks named in `{feedback}`. The `ci_passed` and `ci_failed` events carry `where: "github"`.

Under `build-only` GitHub's checks are the only gate after ship and in the merge step, and `ns` waits for the checks that have registered on the head, so the repo's branch protection should require its CI check. Otherwise a late-registering check can be missed.

`every-step` keeps the local merge queue, configured by `local_queue` as above.

GitHub's merge queue needs an organisation-owned repo. A repo owned by a personal account can still use `build-only`: the merge step then tests the PR head on GitHub, and updates it and waits for CI again only when the default branch changed one of its files. A change in one file that breaks code in another can then land untested, and main's CI and the fix-main path catch it (ADR-648). To test every merge result before it lands, keep `[gate] local = "every-step"` (the default) with `[merge] local_queue = true` (the default): the local merge queue tests each one on the laptop. `ns factory validate` warns, without failing, when `build-only` is set and `gh api repos/<owner>/<repo>` reports the owner's type as `User`. It looks up `origin`'s repo only on GitHub, and gives no warning when `gh` is missing or the lookup fails.

## Updating only on overlap

Outside the local merge queue (under `build-only`, with `local_queue = false`, or with no gate), a PR behind its base is updated only when the base changed one of its files. The step takes the merge base of the PR head and the tip of `origin/<default>` it fetched, and compares `git diff --name-only --no-renames <merge-base> <tip>`, what the PR lacks, with `git diff --name-only --no-renames <merge-base> <PR head>`, what the PR changes. Paths match exactly, and a rename counts as both its paths.

- No path in both lists: the step logs `merge_update_skipped` (`pr`, `base`, `pr_files`, `base_files`) and skips the update. The gate, if one runs here, and the CI wait both run on the PR head as it is, so CI that already passed there counts.
- A path in both: the step logs `merge_update_needed` (`pr`, `overlap`) and updates as before.
- Either list can't be read, such as when the PR head isn't in the worktree, or the two share no history: the step logs `merge_update_needed` with `overlap: null` and the `error`, and updates as before. A fetched tip already in the PR head, though GitHub reports it behind, is logged the same way with a `reason` in place of the `error`, and updates as before.

The check runs again under the merge lock when the base moved during CI (step 5). A head GitHub made by `update-branch` isn't in the worktree, so after an update the check can't read the lists and the PR goes round as before.

With the local merge queue on, nothing here applies: the queue gates the merge of the PR head with the base, which tests the combination itself.

Branch protection that requires PRs to be up to date makes GitHub refuse to merge a PR whose update was skipped, and the unit ends `stuck` with GitHub's error. Turn that rule off to use the skip.

## Red main holds merges

Outside the local merge queue, before it takes the merge lock (step 5, and before it holds the lock through CI past the fifth move), the step reads the CI on the default branch's head with the query `ns watch` uses for main's CI ([watch.md](watch.md#mains-ci)). Red, with every check finished and one failed, holds the merge: the step logs `merge_held_main_red` (`pr`, `sha`) once per red head and reads again with the backoff of step 4. A head that is still red after `ci_timeout_minutes` ends the unit `stuck` with "main's CI is red at <sha>; not merging until it is fixed". Checks still running (even with another failed), or none, don't count as red, and a query that fails holds nothing. The unit working the issue `ns watch` filed to fix main (titled `fix: main is red at ...`) is never held, since its merge is what turns main green. With the local merge queue on, the step doesn't read main's CI: the queue's gate on the merge with the base is the check there.

## Marked regions

`human_review` guards whole files. To guard part of a file, fence it. A region runs from a line containing `ns:human-review start`, optionally followed by `: <reason>`, through the next line containing `ns:human-review end`, marker lines included. Detection is by substring, so any comment syntax works. `start` and `end` may be followed by anything except a letter, digit, `_`, `-`, a quote or a backtick (so `start*/` and `end-->` count, but `endpoint` and a marker quoted in backticks do not). A firmware project fencing its brake limits, with the keyword written as `[ns:human-review]` so this page holds no live marker; drop the brackets in real code:

```c
int brake_ramp(int now) { return now * 2; }

/* [ns:human-review] start: brake torque limits, signed off by the safety lead */
#define MAX_TORQUE_NM 420
#define TORQUE_RAMP_MS 150
/* [ns:human-review] end */
```

A PR that changes `brake_ramp` merges on its own. One that changes `MAX_TORQUE_NM`, or moves or deletes either marker, ends at `done` with "changes code in a human-review region; needs a human merge (src/brake.c:3-6: brake torque limits, signed off by the safety lead)".

`ns check-markers [path]` checks every tracked file and exits 1 on a start with no end, an end with no start, or a start nested inside a region, naming file and line. Run it in CI next to the tests. `ns-no-comments` keeps marker lines. nightshift marks no regions in its own code; this example is the only one in the repo.
