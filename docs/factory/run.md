# ns run

```
ns run <unit-id> [--issue <n>] [--from <phase>] [--gates stop|auto] [--dry-run] [--factory <dir>]
ns run --issue <n>                 # unit id <n>-<slug from the issue title>
ns run <unit-id> --base origin/main   # base for a new worktree (ns watch passes it)
ns run <unit-id> --cpus 4             # CPU share for every phase and gate (ns watch passes it)
```

Steps:

1. Create or reuse the worktree (`ns worktree new`, including setup, which runs again on a worktree whose setup never finished). Worktrees are created one at a time per repo: `ns worktree new` holds the worktree lock, an OS `flock` on `ns-worktree.lock` in the common git dir, from before it lists the worktrees until the new one and its `.ns/<unit>/` exist, and waits while another holds it. `git worktree add` from a remote base writes the branch's upstream to `.git/config`, and two at once fail to lock it. Setup runs after the lock is let go.
2. Read `.ns/<unit>/*.md` frontmatter and pick the next phase from the state table.
3. Archive superseded artifacts. Before running phase P, move P's artifact, if present, to `.ns/<unit>/history/<artifact>-<n>.md`, with n one past the highest number already there for that artifact. Also archive every downstream artifact (order: brief, build, evidence, review, fix, pr) unless it is `status: pass` and current, and every downstream artifact after one that was archived. Whatever remains in `.ns/<unit>/` is current, so the state table needs no timestamps. Inside a review loop (see "Review loop") a review pass keeps `review.md` and archives `fix.md`, and verify keeps both. An archived `review.md` takes `review/cycles.json` with it, to `history/review-<n>/cycles.json`.
4. Take the phase's runner locks (see ["Runners"](../FACTORY.md#runners)), waiting for any that another run holds. Run the phase's harness headless in write mode (`command_write`), with cwd set to the worktree and the rendered prompt on stdin. The phase starts in its own session and process group, so a `kill 0` inside it can't reach `ns`. Its environment carries `NS_UNIT`, `NS_PHASE`, `NS_ATTEMPT`, `NS_WORKTREE`, `NS_RUN_PID` (the `ns run` process running the unit) and `NS_WATCH_PID` (the `ns watch` process, empty under a standalone `ns run`; under watch, the parent of `NS_RUN_PID`, since each unit runs as its own `ns run`; a triage-only run, which `ns watch` runs itself, has both set to `ns watch`). `TMPDIR` is the phase's own scratch directory, a new, empty `<system temp dir>/ns-<repo>-<hash>-<unit>/<phase>-<n>/` with mode 0700, so parallel units never share a file in `/tmp` (the contract's "Scratch files" rule). The system temp dir is the `TMPDIR` `ns run` inherited, else `/tmp` (also when the inherited one is a relative path, which would resolve differently in the phase's worktree), `<repo>` is the main checkout's directory name, and `<hash>` is eight hex digits of a SHA-256 of the git common dir's path, so two checkouts with the same name and unit never share a directory. It sits outside the repo, so the hook guard sees no write into `.git`. Where bubblewrap runs, the phase also gets that directory as its `/tmp`: `ns run` starts the harness under `bwrap --dev-bind / / --bind <TMPDIR> /tmp`, same user, same `/proc` and `/dev`, so a literal `/tmp/<name>` lands in the phase's own `TMPDIR` and no file in the host's `/tmp` is visible. Each host `/tmp` entry that holds a path the phase needs (its `TMPDIR`, the worktree, the git common dir, the `ns` binary, `HOME`, a `PATH` directory, or `SSH_AUTH_SOCK`) is bound back at its own path, which leaves an empty directory of that name in the phase's `TMPDIR`. A process the phase leaves running loses those paths once a passing phase's directory is removed. `ns run` checks at start that `bwrap` runs. When it is not on `PATH`, or fails (user namespaces turned off), phases run as before and share the host's `/tmp`: `ns run` prints a warning and logs a `tmp_not_isolated` event with the reason once per run, and never fails for it. `ns doctor` reports which applies under `private_tmp`. `n` is the first number from the attempt not already taken. `ns run` refuses to start the phase when `ns-<repo>-<hash>-<unit>` is not a directory that only the operator's user owns and can use, since another user of a shared `/tmp` could have made it first. A phase that passes has its directory removed. A failed, blocked, timed-out or interrupted phase keeps it for a human to read until the unit's cleanup (see "Cleanup"), and a later `ns run` of the unit leaves it alone and takes the next free number. Enforce the timeout by killing the process group. The built-in `claude` write command for `ns run` is `claude -p --permission-mode bypassPermissions --model {model} --output-format stream-json --verbose`: the phases need Bash, which `acceptEdits` can't grant headless. The built-in `codex` one is `codex exec --sandbox danger-full-access -m {model}` (see "Codex phases"). A configured claude command gets `--output-format stream-json --verbose` added if it lacks them. Stdout goes to `<git-common-dir>/ns/transcripts/<unit>/<phase>-<attempt>.jsonl`, and cost and tokens are parsed from it.
5. The attempt wrote its artifact if P's artifact exists after the run. An `ns-artifact/2` artifact (one with a `schema:` key) is read through `ns artifact check`'s rules (see [`ns artifact`](../cli/artifact.md)): `cause`, `next` and `reason` replace the body's first line in the state table below (`cause: base_moved` is the `base moved` line, a ship's `next: verify` or `next: review` names that phase, and `reason` is the quoted reason). One that fails the check counts as absent. The run log gets an `artifact_invalid` event (`phase`, `attempt`, `errors`, `archived`), the file moves to `history/<artifact>-invalid-<n>.md`, and the phase runs again with the errors as `{feedback}`. That rerun uses no attempt the first time per phase in an invocation. An artifact without `schema:` is read as `ns-artifact/1`, as before. If not, the attempt failed with "no artifact written" (or the timeout or exit code), and the files archived in step 3 move back, so the next decision sees the state as it was. A triage run that exits 0 without writing `brief.md` is the "triage decided a human or define is needed" row: stuck, no retry. A usage-limit stop also moves the files back (see ["Billing"](../FACTORY.md#billing)).
   A phase killed at its timeout wrote nothing, whatever it left behind: its artifact moves to `.ns/<unit>/history/<artifact>-timeout-<n>.md` (n one past the highest timeout archive for that artifact), the attempt fails with "timed out after <n> min", and the run log's `phase` event names the archive as `archived`. When the phase then runs out of attempts, the stuck reason says the last attempt timed out and suggests raising its `timeout_minutes` or splitting the unit. `NS_PHASE_TIMEOUT_MS` overrides phase timeouts, for tests: `<ms>` for every phase, or `<phase>=<ms>[,<phase>=<ms>]` for the named ones.
   A phase that hit the memory cap (see "Memory cap") or was killed by a signal `ns` didn't send is cut short the same way: its artifact moves to `history/<artifact>-killed-<n>.md`, the attempt fails with "exceeded the <n> MB memory limit" or "was killed by SIGKILL" (the signal's name), and when the phase runs out of attempts the stuck reason ends with that, as in "build is out of attempts (2): the last attempt exceeded the 16384 MB memory limit".
6. Run the CI gate after a build that wrote `status: pass`, and after any other phase that moved HEAD, except ship under `[gate] local = "build-only"` (see "Gate"). A red gate sends the unit back to build, or to a review fix cycle when review's commits caused it.
7. Repeat until the unit is done, merged, split, stuck, paused, or out of budget.

An artifact is current when its frontmatter `sha` matches `git rev-parse --short HEAD` in the worktree by prefix (the lengths may differ), or when the unit's diff at that sha has the same `git patch-id` as at HEAD. The unit's diff is `git diff -U0 $(git merge-base <sha> <base> <merged>...) <sha>`, with `<merged>` every parent that a merge on `<sha>`'s first-parent line since `<base>` brought in and that is an ancestor of `<base>` (a merge of any other branch leaves its changes in the diff), so a merge of a newer base than the local `<base>` ref still starts the diff at the merged tip, and `<base>` the one the worktree was cut from (`origin/<base>` instead when that is ahead of the local branch): `--base`, else `origin/HEAD`'s branch (the local branch when present), else the branch checked out in the main worktree (not the literal `HEAD`, a deliberate change from the issue's text), else the detached sha. `git patch-id` ignores whitespace, so a whitespace-only change after review counts as current, and `-U0` leaves out context lines, so a base change next to the unit's lines does too. A rebase or a merge of the base that leaves the unit's lines alone keeps every artifact current; a merge that resolves a conflict in them does not. A sha no longer in the repo is not current. "`sha` ≠ HEAD" below means not current. Because of step 3, an artifact that exists is current. The table, as implemented, checked top to bottom:

| State | Next |
|---|---|
| `brief` split | **split**: child issues replaced the unit; `brief.md` moves to `history/`, so a parent sent back to the queue is triaged afresh |
| any artifact `blocked` | stuck |
| `pr`, `evidence` and `review` pass at HEAD | **done** (then the merge step under `merge.policy = auto`) |
| no `brief.md` | triage with an issue, else stuck "no brief" |
| `brief` not pass | stuck (triage decided a human or define is needed) |
| no `build`, or `build` fail | build (a fail's body is `{feedback}`) |
| no `evidence`, or evidence `sha` ≠ HEAD | verify |
| `evidence` fail | build, with its body as `{feedback}` |
| `review` fail with `next: review`, and a `fix.md` | review: the next pass of the review loop |
| `review` pass with a `fix.md` (a fix cycle for a red gate ran) | review: the next pass of the review loop |
| `review` fail with `next: review`, no `fix.md` | review-fix, or `review.md` blocked at the cycle limit (see "Review loop") |
| no `review`, or review `sha` ≠ HEAD | review |
| `review` fail | build, with its body as `{feedback}` |
| no `pr`, or `pr` pass with `sha` ≠ HEAD | ship |
| `pr` fail whose first line starts with `base moved` (after an optional `NO-GO:`) | build, with its body as `{feedback}` (a rebase, see below) |
| `pr` fail | the phase its body names first (verify or review), with its body as `{feedback}`, else stuck |
| a phase out of attempts | stuck |

`skills/ns-auto` mirrors this table, the archiving and the currency rule for in-session runs; change them together. The skill is authoritative for in-session runs. Intended differences: its done condition comes from the contract, and a stuck unit gets no timeout archive.

When ship takes in the base and that changes only a little of the unit's own diff, verify and review don't start over. If every phase run that moved HEAD since `evidence.md`'s or `review.md`'s sha was ship's (the ledger records each one), the unit's own changes now start from a newer base (a merge of the base or a rebase onto it, not just ship's own commit), and the unit's changed lines differ by at most 40 between that sha and HEAD (CORE-1, counted by `git::interdiff_lines`: the `+` and `-` lines of each diff from the unit's start, per file, without context or line numbers), the artifact is carried forward. A carried `evidence.md` that passed counts as passing, so verify doesn't run again. A carried `review.md` that passed runs review again as a delta review: its `{feedback}` starts "Delta review." and tells it to review only the change between the two shas and to add `delta_of: <sha>` to `review.md`. Its decision reads "review.md sha <sha> is behind a <n>-line change the base brought in: delta review". A larger change, a move by any other phase, or a run with no ledger (after a finished run) reruns verify and review as below. The gate still runs on the new HEAD either way.

A review that commits leaves `evidence.md` stale, so verify runs again before ship; `review.md` carries the new sha and stays valid. A CI failure in the merge step runs build again; build's commit leaves evidence, review and pr stale, so verify, review and ship follow onto the same PR. A ship that changes the unit's diff after review leaves `pr.md` at HEAD but `review.md` stale, so verify, review and ship run again; ship's `max_attempts` bounds the loop. The PR number comes from `pr.md`'s `pr:`, or from the newest archived `history/pr-<n>.md` that names one, so archiving never loses it.

Attempts are counted per invocation, so re-running `ns run` on a stuck unit gives each phase fresh attempts. The counters (attempts, credits, a pending forced phase) live in a ledger that `ns run` writes to `.ns/<unit>/state.json` before each step. A run that finishes, whatever its outcome, removes the file. A run that stops without finishing (a stop signal, a crash, a reboot) leaves it, and the next `ns run` of the unit resumes it, with a `ledger_resumed` event in the run log. A pending forced phase saved at another HEAD is dropped (`"forced_dropped": true`), and the state table decides instead. `--fresh` or `--from` starts a new ledger instead, and so does a file that doesn't parse, with a `state_rederived` event. `ns run --dry-run` reads the ledger the same way, and carries evidence forward as the run does, but logs and writes nothing. A failed write is a `ledger_not_saved` event, never an error. The first run of a verify or review after it passed in this invocation uses no attempt: HEAD moved under the pass, and the rerun failed nothing. Later runs count until it passes again. The attempt number in the transcript name and `NS_ATTEMPT` still counts every run.

A build that runs only because the default branch moved uses no attempt either. That is a build after `build.md` passed, sent back by an `evidence.md`, `review.md` or `pr.md` fail whose first line starts with `base moved` (after an optional `NO-GO:`), or by a conflict in the merge step (`DIRTY`, or a merge of the default branch that conflicts). Before it runs, `ns run` reads `origin/<default>`'s sha with `git ls-remote`, fetches it, and appends to `{feedback}` "The base moved: fetch origin and rebase onto the newest origin/<default> (<sha>). This build costs no attempt.", so build rebases onto the branch as it is now rather than a commit noted earlier. The run log gets a `rebase_after_base_moved` event with `phase`, `attempt`, `onto` (that sha) and `cause` (the decision that sent work back). When the gate after that build goes red, `ns run` reads `origin/<default>` again. If it moved since `onto`, the next build rebases once more at no cost, with the gate's output as `{feedback}` and the cause "the CI gate failed after a rebase and <default> moved since". That extra rebase never leads to another: a red gate after it, or after a rebase onto a default branch that hasn't moved, uses an attempt. Each free rebase needs a new `origin/<default>` sha, so a NO-GO or conflict repeated with the default branch where it was uses an attempt and the loop ends. With no `origin`, the build uses an attempt. A free rebase build that does not pass (no artifact, a timeout or a `fail`) uses one too. A build's own `fail` uses an attempt whatever its body says.

Under `[gate] local = "build-only"` a conflict in the merge step goes back to ship instead (see ["GitHub merge queue"](merge.md#github-merge-queue)), and that ship is free the way a build is: its `{feedback}` says to merge in the newest `origin/<default>` rather than rebase onto it, and "This ship costs no attempt.". When that ship passes and the verify and review reruns it causes move HEAD again, the ship after them is free too, with a `ship_after_base_moved` event (`attempt`) in the run log; any other phase, or the merge step, ends that chain, and such a ship that does not pass uses an attempt. One invocation sends ship back for a conflict at most 5 times: the next conflict ends the unit `stuck` with "ship was sent back 5 times because the base moved (cap 5)" and a `reship_cap` event (`reships`, `cap`).

Hard rules, enforced in code whatever the prompts say:

- Phases never merge, never approve, and never push to the default branch. Only `ns run`'s own merge step merges (see ["Merge"](merge.md)).
- Before the first phase, `ns run` records `git ls-remote origin` for the default branch (skipped without an `origin` remote). After every phase it reads it again. A move to a commit the unit's HEAD doesn't hold is another actor (a human merge, another machine): it is logged as `default_moved_by_other_actor` and becomes the new baseline. A move to a commit the HEAD holds is either this run's push or a merge the phase then rebased onto, as `ns-build` does when another unit or a human merges mid-phase. `ns run` asks GitHub (`gh api repos/{owner}/{repo}/commits/<sha>/pulls`) about each commit the move added along the first-parent line, at most 50. When every one belongs to a merged PR, none of them this unit's PR (from `pr.md` or its newest archived copy) or from its branch `ns/<unit>`, the move is another actor's, logged as above with `prs` naming those PRs. Otherwise this run may have pushed to it: stuck with "default branch moved" and the reason. That fails closed, so a unit also goes stuck when the query fails, when someone pushes straight to the default branch with no PR and the phase rebases onto it, or when one phase sees more than 50 such commits (a large rebase merge).
- After every phase, if the unit has a known PR (`pr:` in `pr.md` or its newest archived copy, a number or a URL ending in one), `gh pr view <n> --json state`. `MERGED` means a phase merged it: stuck with "PR merged by run".
- Phases don't write the operator's personal memory. Every claude phase and `ns eval` trial runs with `CLAUDE_CODE_DISABLE_AUTO_MEMORY=1`, set over whatever the operator's environment says, so nothing lands in `~/.claude/projects/`. Other harnesses don't get the variable. A lesson worth keeping goes through `ns-improve` into a skill, where review sees it. `ns doctor` reports this as `claude_phases.auto_memory: false`.
- Phases don't skip the repo's git hooks. The hooks are a convenience and the gates and CI are the authority ([ADR-550](../decisions/550-hooks-are-a-convenience.md)): the gate runs outside the agent whenever a phase moves HEAD and before the merge step (under `build-only`, GitHub's checks after ship and in the merge step), so a skipped local hook can't land unchecked code. Every claude phase runs with `--settings` naming one `PreToolUse` hook, `ns guard-hooks`, on the Bash, Edit, Write, MultiEdit and NotebookEdit tools. It fails the plain forms early, naming the rule in `skills/ns-contract/SKILL.md` ("Git hooks"): `--no-verify` on `git commit` and `git push`, `-n` on `git commit`, `git -c core.hooksPath=...` (or `--config-env`), `--git-dir`, `GIT_DIR=`, and a write, move or delete of a protected path (see "Tamper check") named literally. It splits a command into words, so a quoted mention (`echo 'git commit -n'`), a comment or a heredoc body passes, and it follows no variable, alias, nested shell or `cd`: it is best-effort, and a form it can't read literally passes to the tamper check and the gate. The hook lives in the phase settings file (see "Pinned skills and phase settings"); nothing in `~/.claude` changes. `ns`'s own git calls (quality records, the skills fast-forward) are not tool calls and are unaffected. Other harnesses get no hook: there the rule lives only in the skills, with the tamper check and the gate behind it. The hook command exits 2 when `ns` fails to run, so a missing binary blocks the call rather than passing it. A harness command that already carries `--settings` or `--setting-sources` is a usage error. `ns ask` run inside a phase gets the phase's settings, hook included; started by hand, outside a unit's phases, it runs without them.
- Phases don't change the protected paths: the tamper check. Before each phase's harness starts, `ns run` reads the common `.git/config` and any `config.worktree` (the common one and the worktree's own), `.git/hooks/`, the worktree's `.githooks/`, the unit's `.ns/<unit>/skills/`, the phase settings file, and each of `.claude/skills` and `.agents/skills` that is a symlink, with the directory it points at when that is not the snapshot. A tracked `.agents/skills` directory is the repo's own and stays editable, and so do the unit's artifacts in `.ns/<unit>/`. After the harness ends, however it ended (passed, failed, timed out, killed, or interrupted by a stop), it reads them again. A path missing or unreadable before the phase is recorded as such, not an error; one unreadable then is never compared or put back, but one that becomes unreadable during the phase counts as changed. Every root is read whole, however many entries it holds or how deep it goes. A file over 16 MiB is not held: it is compared by its size, mode and a SHA-256 of its content read in a stream, so a same-size content swap is seen, but its change is reported and can't be put back (an added one is removed). A git config file is compared by its entries without the `branch.*` keys, since `git push -u` and other units' pushes set upstreams in the shared config, and a change to it is put back key by key, so a `branch.*` key written meanwhile stays; every other path is compared by its bytes, mode and link target. In `.githooks/` a change the phase committed (or rebased in) is the repo's own and passes: only what differs from HEAD, or is untracked, counts (a staged but uncommitted change counts). A skills link's target outside the snapshot is reported and never written. Any other path that changed, appeared or went away is put back as it was, each file through a temporary file and a rename, the phase is logged with `status: tampered` and the changed `paths`, its artifact is archived as `<artifact>-tampered-<n>.md`, and the unit ends stuck with "<phase> tampered with a protected path (<paths>); ns put it back", or "ns could not put it back: <error>" when the restore failed. A phase that tampers and otherwise passes still fails. Each phase run, a rerun or a resumed one included, records the paths again at its start. The check takes well under a second.
- One run at a time per unit. The run lock, an OS `flock` on `ns-run-<unit>.lock` in the common git dir, refuses a second `ns run` of the same unit with exit 5; runs of other units in the repo go ahead. While held, the file records the holder's pid, unit and issue; otherwise it is empty. The kernel drops a dead run's hold, so a file left by a crash is taken over at once. Runner locks, the merge lock (see ["Merge"](merge.md)) and the worktree lock (step 1) are separate and wait instead (see ["Runners"](../FACTORY.md#runners)).

Run log: append one JSON line per event to `.git/ns/runs.jsonl` in the common git dir: unit, phase, attempt, decision, artifact status, sha, cost, tokens, wall time, exit. Start, end, breaches, CI failures, gate runs and merges are events too. `ns run --dry-run` prints the next decision, the rendered prompt and the command, and runs nothing: no worktree, no lock, no harness.

Quality records: when a unit ends `merged`, `done` or `stuck`, `ns run` writes one record per review attempt to the `nightshift/quality` branch on `origin` and logs a `quality_record` event (see ["Quality"](quality.md)). A unit with no review artifact adds no record. A push that fails, or a repo with no `origin`, leaves the records in the outbox and never changes the unit's outcome. Before it writes them, `ns run` finds the conflicts the unit's branch resolved, whoever resolved them: each merge commit in `<base>..HEAD` is merged again with `git merge-tree --write-tree --name-only`, and the paths that conflict go into the records as `conflicts` and into the run log as a `conflict_resolved` event (`merge`, `paths`) per merge. A merge of more than two parents is skipped with a `conflict_skipped` event (`merge`, `reason`). A git failure records nothing for that merge, or for the branch when its merges can't be listed, and logs a `conflict_check_failed` event (`merge` or `range`, `error`); it never fails the unit's end. `ns clean`, when it records a unit a human merged, finds the conflicts in `<base>..<head>`, where `<base>` is the `base:` in the unit's `brief.md` (the default branch without one) and `<head>` is the merged PR's head (the worktree's `HEAD` when the PR head is unknown, and no check at all when `HEAD` is the default branch). It logs only `conflict_check_failed`, since the run that ended the unit logged the other events.

Cleanup: when the merge step merged the unit's PR and its records are saved (pushed, or in the outbox), `ns run` removes the unit's worktree and its local `ns/<unit>` branch and logs a `cleanup` event. A worktree with uncommitted changes to tracked files, or a branch holding changes the merged PR head doesn't, stays. See ["Cleanup"](unit-lifecycle.md#cleanup). A run that ends `done` or `stuck`, or `merged` with its worktree kept, deletes the worktree's build output and logs `build_output_removed`; see ["Build output"](unit-lifecycle.md#build-output).

Budget: before each phase, if the cost reported so far (across the units of one `ns watch`) has reached `limits.budget_usd`, the run ends with `budget`. On a subscription the reported cost is an estimate, so the cap is notional and unset by default; `--until`, an optional `max_units`, and usage-limit pauses bound a night instead.

Output: final JSON `{unit, outcome: done|merged|split|stuck|budget|paused, phase, reason, pr, cost_usd, reset_at, artifact, worktree, cleanup, phases:[...]}`. `cleanup` is null unless the unit merged; then it is `{unit, path, branch, issue, pr, removed}`, with a `reason` when the worktree stays. A `split` names the triage phase, the archived `brief.md` as the artifact, and the reason `brief.md is split: <its first line>`. Exit 0 for done, merged or split, 1 for stuck, 2 for a usage or config error (bad definition, missing subscription login, harness not on PATH), 3 for budget, 4 for paused, 5 when another `ns run` holds the unit's run lock.

## Review loop

`ns run` drives review's fix loop, one phase run per step, each under review's `timeout_minutes`. A review pass that leaves a Critical or Important open in changed code writes `review.md` with `status: fail`, `cause: findings_open`, `next: review` and the open IDs in `findings`. `ns run` then runs a fix cycle: a `review-fix` phase run with `[phases.review]`'s skill, harness, model, timeout, `max_attempts` and runner, whose locks it holds as a pass does (`NS_PHASE_TIMEOUT_MS` takes a `review-fix` entry, else review's). Its `{feedback}` names the cycle, its kind and the IDs to fix, and it writes `fix.md` (`phase: review-fix`) listing them. When the fix moved HEAD, verify runs again, keeping `review.md` and `fix.md`. Then the next review pass runs, told "Review pass <n>, after fix cycle <n> (<kind>)", and updates `review.md` in place. A fix cycle cut short is retried as the same cycle, even when it committed. A `fix.md` with `next: build` sends the unit to build; one that is `blocked` stops it.

A red gate whose output points at review's or a fix cycle's commits (see "Gate") also runs a fix cycle, numbered after the loop's last, with the gate's output as `{feedback}` and `findings: []`. Nothing but the gate's feedback carries it, so a run of it that is cut short, exits non-zero, exits without writing `fix.md`, or writes an invalid one is retried as the same cycle with the gate's output, within `max_attempts`; a valid `fix.md` is followed as above. A loop is then under way though `review.md` passed: `review.md` with a `fix.md` beside it routes to the next pass as above, verify keeps both, and the pass takes up `fix.md`. With no cycle left, the unit ends stuck as below, with the reason "<the gate's reason>, and the review loop has used its <n> fix cycles (limit <full> full, <fix-only> fix-only)".

Cycles 1 to `full_cycles` (default 3) are full: they hand over every ID in `findings`. The next `fix_only_cycles` (default 2) are fix-only: they hand over only the findings whose `Attempts:` in `review.md` is under 2, and the pass after one raises nothing new. When no cycle is left, or a fix-only cycle has nothing to hand over, `ns run` rewrites `review.md` as `status: blocked`, `next: human`, `cause: findings_open` with the reason "review.md has findings open after <n> fix cycles (limit <full> full, <fix-only> fix-only): <IDs>", and the unit ends stuck on that reason; a rerun stops on the blocked `review.md` without running a phase. A human fixes by hand and deletes `review.md` so the next `ns run` reviews afresh, splits the issue, or routes it to `ns-define`.

`ns run` keeps the loop's record in `.ns/<unit>/review/cycles.json`: one entry per pass and fix cycle that wrote a valid artifact, with `phase`, `cycle` (a pass's is the fix cycle it follows, 0 for the first), `kind` (`first`, `full` or `fix-only`), `started` (UTC, on `ns run`'s clock, as the harness starts) and `ended` (`started` plus the harness's wall time) and `sha`. A loop's first pass starts a new record. The cycle count comes from the record, never from the agent, so a rerun after a crash resumes the loop where it stopped. The record fails closed: inside a loop, a record that is missing or can't be parsed ends the unit stuck rather than count from 0, and a pass or fix cycle whose entry `ns` can't write is archived as `history/<artifact>-unrecorded-<n>.md`, its changes undone, and the unit ends stuck. A pass or fix cycle that is cut short, interrupted, writes an invalid artifact, or exits without changing the `review.md` it was given inside a loop leaves the loop as it was: `ns run` puts back `review.md`, `fix.md` and the record as they stood before the run, so the retry is the same pass or cycle. The run log's `phase` event of each loop run carries `review_cycle` (`cycle`, `kind`), and the quality record carries the record as `review_runs` (see [Quality](quality.md)). A pass after a fix cycle, and a fix cycle after a pass, use no attempt; a run that retries the same step does.

## Pinned skills and phase settings

A unit's claude phases run the skills of the commit the unit forked from, not the installed skills and not the worktree's. At unit start, before the first phase, `ns run` takes the merge-base of the base and the worktree's HEAD and writes that commit's `skills/` (every skill, so links like `../ns-principle-*` resolve) and `.agents/skills/` into `.ns/<unit>/skills/`, as real files read from git objects through a scratch index, so neither the worktree nor its index changes. A repo whose `skills/` tree holds no `ns-*` skill, such as a consumer of nightshift, gets the `ns-*` skills installed for its phases' harnesses copied instead, from the first of these dirs that holds any: each phase harness's own, in phase order (`~/.claude/skills` for claude, `~/.agents/skills` for codex, none for another harness), then `~/.claude/skills`, so its snapshot is pinned at unit start rather than to a commit. A snapshot with no `ns-*` skill (none in the repo, none installed) is an error that names `ns install` and each dir it looked in, and an empty snapshot an earlier run left is rebuilt. The snapshot is written once per unit: a resume or a later attempt keeps it, whatever has landed on the default branch or changed in the worktree since. The run log gets a `skills_pinned` event (`sha`, `source` (`base` or `installed`), `skills`) when it is written. The worktree's `.claude/skills` and `.agents/skills` are symlinks to it, both in the repo's git exclude list, so `git status` stays clean; `ns run` replaces only a symlink into a unit's snapshot. A tracked `.agents/skills/` directory (nightshift tracks one) is left as it is, and the snapshot has its skills anyway. A skill in both `skills/` and `.agents/skills/` takes the `.agents/skills/` copy. Any other existing path is left alone: a tracked `.claude/skills` directory or a symlink elsewhere stops the run with a usage error, and a symlink elsewhere at `.agents/skills` gets a warning on stderr and a `skills_unpinned` event (`path`, `why`).

Every claude phase runs with `--setting-sources project,local --settings <git-common-dir>/ns/units/<unit>/phase-settings.json --add-dir .ns/<unit>/skills`. `--setting-sources` leaves out the operator's user settings: neither `~/.claude/settings.json`, with its deny rules, nor the personal skills in `~/.claude/skills` reach a phase. Personal settings stay theirs, for interactive sessions. The settings file is `.nightshift/phase-settings.json`, built into `ns` and written for the unit at every `ns run` start, and again before every phase, with the path of the running `ns` in its hook. The copy a phase reads lives under the git common dir, outside every worktree, so a phase cannot reach it by editing its own worktree; the phase's `NS_PHASE_SETTINGS` names it. Changing the factory's settings is a human merge (`.nightshift/**`). The snapshot has to stay reachable through the worktree's symlinks, so it is guarded rather than hidden: the tamper check (see the hard rules above) puts back any change to `.ns/<unit>/skills/`, to the settings file and to the skills links after each phase, whatever made it, and `ns guard-hooks` denies a write, move or delete that names one of them literally, `$NS_PHASE_SETTINGS` included. A change made during a phase still reaches the rest of that phase; the next phase starts from the snapshot. The settings file denies `Bash(sudo:*)`, `Bash(terraform apply:*)`, `Read(//**/.env)` and `Read(//**/secrets/**)`, and holds the git hook guard (see the hard rules above). Those two `Read` denies bind the Read tool only: `cat .env` in Bash passes, so they are not a secrets boundary, and Claude Code's permission rules can't except a directory from a deny, so they apply inside the unit's worktree too. Keep real secrets out of reach of the phase's user. `ns ask` started inside a phase (with `NS_WORKTREE`, `NS_UNIT` and `NS_PHASE_SETTINGS` set and the settings file there) gives a claude command the same flags. Those variables are the phase's own, so this is cooperative: a phase that clears them asks claude with the operator's settings. It is a usage error when the command already carries either flag, the unit id is not a valid id, or the settings file is gone.

This changes what a claude phase and a claude `ns ask` in one see, and the remedy for each is to move the setting into the repo's `.claude/settings.json` or `.claude/settings.local.json` (project sources still load) or into `.nightshift/phase-settings.json` (a human merge). `--settings` is now a file path, not inline JSON. A harness command with `--settings` or `--setting-sources` is a usage error, so the user config's `command_write` for claude must drop them. The operator's user-level `env`, hooks, MCP servers, `apiKeyHelper` and their own deny rules no longer reach a phase, and neither do their personal skills.

A `.claude/skills` the repo tracks (a real directory, or a symlink that is not a snapshot) is an error at `ns run` start, because claude reads that path and would run unpinned: remove or untrack it, or keep the skills in `.agents/skills`. A tracked `.agents/skills` symlink elsewhere only warns, as no claude phase reads it. `ns doctor` reports both before the first run: a tracked `.claude/skills` as a problem, a tracked `.agents/skills` as a warning.

Codex phases are only partly pinned. `ns run` links the snapshot as the worktree's `.agents/skills` for every harness, so codex reads it as the project's skills, except in a repo that tracks `.agents/skills` (nightshift does): there that live, editable directory stays in place, codex reads it and not the snapshot, and `ns run` warns and logs a `skills_unpinned` event but does not fail. Codex also reads user skills from `~/.agents/skills`, and no per-run switch to turn them off is confirmed (`[[skills.config]] enabled = false` is untested), so a codex phase still loads the installed skills too, which the skills sync can change between units, and which copy wins a name clash is not confirmed. It gets none of the claude flags (`--settings`, `--setting-sources`, `--add-dir`). So on a night with codex phases, `ns watch` drains before it syncs a skill change (see the skills sync under ["ns watch"](watch.md)). `ns doctor` reports the mode per harness: `pinning` is `snapshot` for claude, `partial` for codex (it reads the project's `.agents/skills` next to the user's), and `none` for cursor-agent, gemini and opencode, whose skill lookup is not confirmed (cursor-agent's is unconfirmed in its docs). Each harness's `skills_from` lists the dirs a unit on that harness alone takes installed skills from.

## Codex phases

A codex phase runs `codex exec --sandbox danger-full-access` unless the user config sets a `command_write` for codex, which is used as written. Codex's `workspace-write` sandbox blocks the network and writes outside the worktree, so `git push`, `gh` and a commit in a linked worktree (whose git dir sits in the main checkout's `.git`) fail under it. `ns ask --write` keeps `workspace-write`, as it runs without the guards below.

With codex's sandbox off, two guards of `ns run`'s own, which apply to every harness, stand in for it:

- The private `/tmp` (step 4): under bubblewrap the phase gets its `TMPDIR` as `/tmp` and sees no file in the host's `/tmp`.
- The tamper check ("Phases don't change the protected paths"): a phase that changes the git config, the hooks, the skill snapshot, the phase settings or the skills links is failed as `tampered` and the path put back. Codex gets none of claude's phase settings, so this check is its only deny.

Neither guard stops a codex phase from reaching the network or writing elsewhere under the operator's home; the gates and CI decide what lands ([ADR-550](../decisions/550-hooks-are-a-convenience.md)). `ns doctor` reports, per harness, `private_tmp` and `skills_from` (see "Pinned skills and phase settings", for where pinning takes installed skills from).

Not done for codex yet: cost and tokens (`ns run` parses them only from claude's `stream-json`; codex's `--json` output is not read, so a codex phase reports no cost and counts nothing toward `limits.budget_usd`), and usage-limit pauses (a codex phase that hits its plan's limit fails as any other phase does, with no pause until the reset).

## Gate

Build's artifact is the agent's own word that checks pass. The gate is a deterministic check `ns run` runs itself, so a commit that fails CI goes back to build before the next phase, and never reaches a merge.

The command is `[phases.build] gate`. Unset, it is the `ci-local` row of the Commands table in `docs/agents/stack.md` in the main checkout: a table row whose first cell is `ci-local` (backticks optional), with the command as the backticked span that opens the second cell (it may contain `|`):

```markdown
| ci-local | `scripts/ci-local.sh` | 2 min |
```

With neither, no gate runs. When `stack.md` has a `rules` row (see "Rules"), the gate is the command above followed by `&& <ns> rules check --prune`, or `<ns> rules check --prune` alone when there is no command, where `<ns>` is the path of the running `ns` binary. When `nightshift.toml` defines a ratchet (see "Ratchets"), `&& <ns> ratchet check --human` comes last, or runs alone. Both are read from the main checkout when `ns run` starts, so a phase can't change the command. The script it runs lives in the worktree, though, so the gate is not tamper-proof.

`ns run` runs the command with `sh -c` in the worktree after a build that wrote `status: pass`, after any other phase that moved HEAD (a verify or review fix that committed, a ship that merged the base in), and in the merge step before it merges: on the PR head, or on its merge with the default branch when the local merge queue is on (see ["Merge"](merge.md), step 3, and ["Local merge queue"](merge.md#local-merge-queue)). Under `[gate] local = "build-only"` neither a ship that moved HEAD nor the merge step runs a gate: GitHub's checks decide the merge (see ["GitHub merge queue"](merge.md#github-merge-queue)). A build that wrote `fail` or `blocked` runs build again, so no gate runs after it; neither does a triage-only run. It doesn't run again at a HEAD where it already went green in this invocation, so a phase that leaves HEAD alone never re-runs it. It is killed at the build phase's `timeout_minutes` (`NS_GATE_TIMEOUT_MS` overrides it, for tests). Only the last 16 KiB of its log are read for the tail. Output goes to `<git-common-dir>/ns/transcripts/<unit>/gate-<phase>-<attempt>.log`.

Exit 0 is green and the run goes on as the state table says. When the gate's `ns rules check --prune` dropped fixed entries from the rules baseline (see "Rules"), the gate after build keeps them dropped: after it goes green, `ns run` commits `.nightshift/rules-baseline.json` alone, with the hooks skipped since the full gate has just run, as `chore(rules): drop fixed entries from the rules baseline`, so the PR carries the shrink and the merge step lets it through (see ["Merge"](merge.md), step 6). It does this only when the file in the worktree differs from HEAD's by removed entries and refreshed messages alone, never for a baseline a phase grew, broke or left untracked. The commit changes nothing the gate checks, so the green verdict holds at it, and `build.md`'s `sha` moves to it when build.md was written at the gated HEAD; no phase runs again for it. The run log gets a `baseline_pruned` event (`phase`, `from`, `to`). Every other gate, and a red one, restores the file from HEAD. A non-zero exit, a signal, the memory cap or the timeout is red: the next phase is build, with the command, how it failed and the last 40 lines of its output (at most 3000 bytes) as `{feedback}`. How it failed names the signal ("was killed by SIGKILL") or the cap ("exceeded the 16384 MB memory limit") when one ended it, and so does the stuck reason: "build is out of attempts (2): the CI gate exceeded the 16384 MB memory limit". That build uses an attempt against `max_attempts`, so a gate that stays red ends with "build is out of attempts". `ns run` records each phase run that moved HEAD, takes the files the gate's output names (`path:line` in compiler errors, test panics and rule findings), and charges the red to the newest phase run whose commits changed one of them. The run log gets a `gate_fault` event (`phase`, `attempt`, `culprit`, `paths`). The charge decides where the fixing work goes: a red charged to build, or one that names no file any phase changed (such as one the base caused), is charged to build as before, so that build uses an attempt. When the charged phase is review or a fix cycle (`review-fix`), no build runs: the next phase is a fix cycle with the gate's output as `{feedback}`, then the review loop's next pass, as after any fix cycle (see "Review loop"). That fix cycle counts against the loop's `cycles`, and once they are spent the unit ends stuck with `review.md` marked blocked, its reason naming the red gate and the cycles used. When the charged phase is any phase but build, review or a fix cycle (ship, verify, triage, or a phase added later), the build that fixes it uses no attempt, at most 6 times per invocation, one counter shared across every phase's fault rather than 6 per phase (CORE-4 in `docs/design/factory-core/v1.md`). A free fix that doesn't pass uses an attempt after all. Each run is a `gate` event in the run log with `phase` (the phase it followed, or `merge` for the run in the merge step), `attempt`, `command`, `sha`, `exit`, `signal`, `timed_out`, `memory_exceeded`, `wall_s`, `green` and `log`. Its `where` is `local_full` for the full command and `local_fast` for the fast one (see "Where the gate runs all of CI"); the merge step's `ci_failed` and `ci_passed` events carry `"where": "github"`. `ns run --dry-run` shows the full command as `gate` and the one every other gate runs as `gate_rest`.

This repo's `scripts/ci-local.sh` keeps a pass cache, so the gate, the merge queue's gate and the pre-push hook don't test a tree that already passed (ADR-444). A full run that passes writes one small file in `<git-common-dir>/ns/ci-passed/`, which every worktree of the repo shares, keyed by the tree it tested and the SHA-256 of the pins in `scripts/ci-tools.d/` and of `scripts/ci-local.sh`. The tree is the index's (`git write-tree`): a commit's tree in a clean checkout, or the merge result staged in the merge queue's scratch worktree. A later full run on the same key prints `ci-local: tree <hash> already passed (<when>, <where>)` and exits 0. The cache is not used when the working tree differs from the index or holds an untracked file, and a run is not recorded when the tree changed while it ran. Only passes are recorded. `--no-cache` runs anyway, and `--fast` neither reads nor writes the cache. It keeps the 200 entries used last (`CI_LOCAL_CACHE_MAX` overrides it, for tests).

### Where the gate runs all of CI

`[gate] local` says which gates run the full command above:

- `every-step` (the default): every gate runs it, after build, after any other phase that moved HEAD and in the merge step.
- `build-only`: only the gate after build runs it. No local gate runs after ship or in the merge step; the PR's GitHub checks decide, and the GitHub merge queue replaces the local one (see ["GitHub merge queue"](merge.md#github-merge-queue)). The gates after verify and review run the fast command: the base command (`[phases.build] gate`, else the `ci-local` row) with ` --fast` appended, then the `ci-affected` row of `stack.md`, as `(<base> --fast) && (<ci-affected>)`, either part alone when the other is missing, and no gate when both are. The `rules` and ratchet checks run only in the full command; a `ci-affected` command can run the rules itself, as this repo's runs every `rules` row command (`ns rules check`) on a change under `cli/` and only the ast-grep ones (`ns rules check --only ast-grep`) otherwise. A red fast gate goes back to build like any red gate, and the rebuild's gate is the full one. A fast gate is skipped at a HEAD where the full one already went green.

So under `build-only` the base command must accept `--fast`, as this repo's `scripts/ci-local.sh` does; under `every-step` it needs no flag. `ns factory validate` warns, without failing, when `build-only` is set and the base shows no `--fast` support: the `[phases.build] gate` text, or every `ci-local` row of `stack.md`, never names `--fast`. A missing row or a row of `none` gets no warning. It also warns when `build-only` is set and GitHub reports the repo's owner as a personal account, whose repos have no GitHub merge queue, so the merge step tests the PR head and updates it only when the default branch changed one of its files (see ["GitHub merge queue"](merge.md#github-merge-queue)). The `ci-affected` command runs with `NS_GATE_FILES` set to the paths, one per line, that differ in the gate's checkout from the HEAD where the full gate last went green in this invocation, else from the merge base with the unit's base. It runs the tests those paths need; this repo's is `scripts/ci-affected.sh`. Any other gate leaves `NS_GATE_FILES` unset.

This repo's `.githooks/pre-push` reads `[gate] local` from `.nightshift/nightshift.toml` in each commit pushed, and runs `scripts/ci-local.sh --fast` there under `build-only`. GitHub CI still runs everything before the merge step merges. This repo sets `build-only` (ADR-466).

## Rules

A rule pack is the set of linters and pattern checkers a repo runs to enforce its rules (`ruff check`, `ast-grep scan`, `cargo clippy`, `cargo deny check`). `ns rules check` runs it and fails only on violations a committed baseline doesn't list, so existing code never blocks a unit. The commands are every backticked span that opens the second cell of the `rules` row in `docs/agents/stack.md`, separated by commas or spaces:

```markdown
| rules | `ruff check --output-format=concise .`, `./scripts/rules-ast-grep` | 10 s |
```

Nightshift ships one pack per language under `rules/<language>/`, and `ns-setup` installs one into a repo's `.nightshift/rules/<language>/` with its row. `rules/README.md` lists the packs, and `ns lint` checks that it names exactly the directories under `rules/`. Each pack lists its rules in its README.

Each command runs with `sh -c` at the top of the git checkout it is started in. Every line it prints, on stdout or stderr, that is a finding is read as one:

- a JSON object with `file`, and optionally `tool`, `rule`, `line`, `message` and `snippet`
- `file:line[:col]: message`, the format most compilers and linters can print; its `rule` is empty

`tool` defaults to the command's first word without its directory (`./scripts/rules-ast-grep` is `rules-ast-grep`). A path under the checkout is made relative to it. `snippet` defaults to the source line at `file:line` with whitespace collapsed, else the message. Other lines are ignored, so a tool that prints neither format needs a wrapper script that converts its output (for example its JSON, with `jq`). A command that exits non-zero and prints no finding is an error: a linter that isn't installed must not read as clean. So is a command that is killed by a signal or exits 126 or 127, even after printing findings, one that runs longer than 300 s (`NS_RULES_TIMEOUT_MS` overrides it, for tests), and one that prints more than 8 MiB (`NS_RULES_MAX_OUTPUT_BYTES` overrides it, for tests): output past the cap would hide findings, so it fails instead of being cut. The error shows the last 20 lines of the output.

The baseline is `.nightshift/rules-baseline.json`: `{"version": 1, "violations": [<entry>...]}`, sorted. An entry is a finding without its line (`tool`, `rule`, `file`, `message`, `snippet`), so a line shift leaves the file unchanged; a `line` in an older file is ignored. A finding matches a baseline entry when `tool`, `rule`, `file` and `snippet` are equal, so a line that moves still matches, and matching counts: two identical findings need two entries.

`ns rules check` prints `{ok, command, baseline, commands, findings, baselined, new, fixed, pruned}` and exits 1 when `new` is not empty. `fixed` lists baseline entries nothing matched, with no line, since the baseline stores none. A fixed entry is reported, never a failure: a run with only fixed entries exits 0. `--prune`, when `new` is empty, rewrites the baseline without the fixed entries and keeps every other entry as the file had it, so it can only shrink the file; `pruned` is how many it dropped, 0 when it wrote nothing. The gate runs it (see "Gate"). With no `rules` row it runs nothing and exits 0, which is why CI and `scripts/ci-local.sh` can run it unconditionally.

`ns rules check --only <text>` runs only the `rules` row's commands that contain `<text>`, against the same baseline. Its `fixed` is always empty, since the baseline entries of the commands it skipped would read as fixed, so with `--prune` it writes nothing. When the row has commands but none contains `<text>`, it is a usage error (exit 2) listing them; with no `rules` row it runs nothing and exits 0, as without `--only`.

`ns rules baseline` writes every current finding to the baseline. It is a ratchet: entries that are gone are dropped, and a finding the baseline lacks, every finding when there is no baseline yet, is growth. Without `--allow-growth`, growth writes nothing and exits 1 with status `refused`. `--allow-growth` is for a human accepting debt, never for an agent. A finding whose entry has another message keeps matching, so `ns rules check` passes; `ns rules baseline` writes its new message to the entry, and `refreshed` counts such entries (the human summary adds ", N refreshed" when there are any). A run whose file would come out byte for byte the same writes nothing (`already-done`), and `--dry-run` writes nothing (`planned`). `.nightshift/**` needs a human merge in this repo, but a baseline change that only removes entries or refreshes their messages merges without one (see ["Merge"](merge.md), step 6); growth, or an entry with a new `tool`, `rule`, `file` or `snippet`, still needs a human.

A Rust pack ships in `rules/rust/` (D54): clippy, cargo-deny and ast-grep behind `check.sh`, which `ns-setup` installs into a Rust repo's `.nightshift/rules/rust/` with `install.sh`. Its repo-owned lists are `allowed-crates.txt` (every crate the dependency graph may hold) and `roads.txt` (the helpers a second definition of would duplicate). Clippy runs with `--keep-going`, so a member that fails to compile or fails a lint doesn't stop the other members being linted; a member that depends on one that doesn't compile can't be built, so it isn't linted. A compile error is therefore not a finding (D58): `check.sh clippy` exits 2 with no findings and prints the errors, and the findings from the members it did lint, as `check.sh:` lines on stderr, so `ns rules check` fails as broken and `ns rules baseline` records nothing, as with the C pack. Lints, clippy's and rustc's, stay findings.

## Ratchets

A ratchet holds a measured value, such as binary size, flash or RAM use, coverage or a warning count, to the value recorded for it, so a unit can't grow an image or drop coverage unnoticed (ADR-415). Any command that prints one number can be one. Each is a table in `nightshift.toml`:

```toml
[ratchets.flash]
command = "scripts/flash-size.sh"   # run with sh -c at the top of the checkout
better = "lower"                    # or "higher"
tolerance = "0.5%"                  # of the recorded value, or an absolute number like 1024; default 0
```

The recorded values are in `ratchets.json`, next to `nightshift.toml`: `{"version": 1, "values": {"<name>": <number>}}`. Both files are human-review in this repo (`.nightshift/**`). A unit never edits either: loosening a ratchet is a human decision.

The Python, Rust and C rule packs each ship an example ratchet, a script and its tables in the pack's `ratchet.toml`: coverage under pytest-cov (`rules/python/`), a binary's size (`rules/rust/`), and an ELF image's flash and RAM (`rules/c/`). `ns-setup` offers the ones that fit a repo.

`ns ratchet check` runs each command and reads what it printed on stdout as one number. A command that exits non-zero, is killed, runs over 300 s (`NS_RATCHET_TIMEOUT_MS` overrides it, for tests), or prints anything but one finite number is `broken`. A value worse than the recorded one by more than the tolerance is `worse` (when the command runs twice, the worse of the two runs is the `measured` value, so the order of the runs never changes the verdict, and `update` records that value too); the limit is `recorded + tolerance` when lower is better, `recorded - tolerance` when higher is. A percentage is of the recorded value. A ratchet with no recorded value is `untracked`: reported, never failed, and nothing is recorded. Otherwise it is `ok`, or `better` when it beats the recorded value. A flaky metric is a bug, so each command runs twice, and two values further apart than the tolerance (a percentage of the recorded value, else of the first run) make the ratchet `flaky`. Under `ns watch` only a ratchet's first check of the night runs twice: the gate points `NS_RATCHET_STEADY` at `ratchets-steady.json` in the night directory, which lists the ratchets that passed a double run tonight. Without it, as in CI or a plain `ns run`, every check runs twice. It prints `{ok, command, recorded, ratchets: [{name, command, better, tolerance, recorded, measured, runs, limit, status, error}]}` (`--human` prints one line per ratchet) and exits 1 when one is `worse`, `broken` or `flaky`. With no ratchets it checks nothing and exits 0, so CI and `scripts/ci-local.sh` run it unconditionally.

In the gate (see "Gate") `ns run` sets `NS_RATCHET_FACTORY` to its factory directory, so the check reads the definition and values the run started with, not ones a unit edited in its worktree, and `NS_RATCHET_REPORT` to `gate-<phase>-<attempt>.ratchets.json` beside the gate log, where the check writes its JSON too. When that report names failed ratchets, the feedback to build names each one with its measured value, recorded value, tolerance and limit ("ratchet flash is worse: measured 120, recorded 100, tolerance 5%, limit 105, lower is better") and tells build not to edit the ratchet, and a unit that runs out of build attempts ends stuck with "build is out of attempts (2): the CI gate failed on ratchet flash is worse: ...". `--factory <dir>` wins over `NS_RATCHET_FACTORY`, which wins over `.nightshift/` in the main worktree.

`ns ratchet update` is for a human or a scheduled job, never a unit. It measures every ratchet twice and records the values: an `untracked` ratchet is `recorded`, a better one `tightened`, an equal one `unchanged`. A worse value, even within the tolerance, is `kept` at its recorded value, so tolerance can't creep the line; `--allow-loosen` records it (`loosened`). Values of ratchets no longer defined are dropped. A broken or flaky ratchet writes nothing and exits 1 (`refused`). A run with nothing to change writes nothing (`already-done`), and `--dry-run` writes nothing (`planned`). Commit the result; it needs a human merge.

## Memory cap

One runaway test binary can take all of a machine's memory and, with it, the night. `[limits] memory_mb` caps each phase and each gate run at that many MiB. It is off by default. Under the cgroup the cap covers the run with everything it starts; under the RLIMIT_AS fallback it applies to each process on its own (see below).

When it is set, `ns run` and `ns watch` probe once at start (a dry run doesn't) and print which mechanism they use; each unit's `start` event in the run log records it as `memory_cap: {mb, via, fallback}`. With a cap set, `ns run` checks that the harness binary exists before wrapping it, so a missing one is still the usage error, exit 2.

- **cgroup** (`via: "systemd-run"`), where `systemd-run --user` accepts the scope's properties and sets its `memory.max` (the probe starts a scope with the same properties as a real run): the command runs as `systemd-run --user --scope -p MemoryMax=<n>M -p MemorySwapMax=0 -p OOMPolicy=stop`. At the cap the kernel kills a process in the scope and systemd stops the rest. `ns` reads the scope's result from systemd (`oom-kill`), so the cap is detected exactly. Once the run is over, on every path (an exit, a timeout, a kill, a stop), `ns` waits up to 10 s for the scope to stop and then runs `systemctl --user reset-failed` on it, so failed scopes don't pile up in `systemctl --user --failed`.
- **RLIMIT_AS** (`via: "prlimit"`), otherwise: the command runs as `prlimit --as=<bytes>`, and `fallback` says why the cgroup wasn't used. Nothing is killed at the cap. An allocation past it fails and the program decides what to do. `ns` counts a run as over the cap when it failed and its output (the gate log's tail, or the harness's stderr) holds a line with a common allocation-failure message (Rust's `memory allocation of <n> bytes failed`, a line starting `MemoryError`, `std::bad_alloc`, `Cannot allocate memory`, Go's `fatal error: runtime: out of memory`, V8's `Fatal process out of memory`). That is a heuristic: a failure that prints none of them reads as an ordinary failure. The limit is per process, not per run: each process the run starts gets its own `memory_mb`, so `cargo test` or `make -j8` can use many times the cap in total. RLIMIT_AS also counts reserved address space, not memory in use, so runtimes that reserve large ranges (sanitizers, the JVM, Go, V8) need a cap well above what they use.
- Neither works: `ns run` and `ns watch` exit 2 before any phase runs.

A phase or gate over the cap fails that attempt with "exceeded the <n> MB memory limit" (see step 5 and "Gate"), the unit carries on or goes stuck through the normal attempt rules, and `ns watch` goes on to the next unit.
