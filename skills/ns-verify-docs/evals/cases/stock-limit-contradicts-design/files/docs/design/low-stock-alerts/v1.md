## Goals

- STOCK-1: `status` marks each item whose available stock is below its threshold.
- STOCK-2: a `low-stock` command lists every low item, one per line.
- STOCK-3: `reserve` and `fulfil` stay inside the slowdown STOCK-3 allows.

## Non-goals

- Ordering from the supplier (STOCK-5).

## Design

Each item gains an optional `threshold` field in the JSON state file. A missing field means no threshold, so an older state file loads unchanged and its items never show as low.

`Warehouse.available(sku)` already computes on hand minus unexpired reservations. `status` and `low-stock` compare it with the threshold when they print. Neither changes `reserve` or `fulfil`.

To keep `low-stock` fast on large stores, `reserve` and `fulfil` update a set of low SKUs as they change stock. Measured on a 10,000-item store, this adds 8% to the median `reserve` call, inside the 10% STOCK-3 allows.

## Alternatives

- **Do nothing**: purchasing keeps reading the full `status` table each morning.
- **Compute low items on read only**: no cost to `reserve`, but `low-stock` reads every item, 40 ms on a 10,000-item store.

## Failure modes

- The low-SKU set drifts from the stock figures after a crash between the two writes. Detected by `low-stock --check`, which recomputes the set and reports any difference.

## Privacy

No personal data. Thresholds and SKUs only.

## Security

No new input reaches a shell or a file path.
